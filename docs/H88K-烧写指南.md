# H88K 烧写与上板指南（友善 Android 14 底包）

> 目标板：HINLINK H88K V3（RK3588 / 8GB / 64GB eMMC / NVMe 931G）
> 底包：友善 `android-14-images-rk3588.tgz`（Android 14 Tablet，version 20251222）
> 本仓做的事：把底包 boot 分区里的 12 个 `rk3588-nanopi6-rev*` dtb 全换成 H88K 的，
> 并把开机第一家 logo 换成 H88K 的。

## 一、这次产出了什么

| 文件 | 大小 | 说明 |
|---|---|---|
| `out/h88k-a14-sd-8g.img` | 8.00 GiB | **整盘 SD 镜像，直接写卡就能启动** |
| `build/boot-rk3588-h88k-a14.img` | 53.50 MB | 只改 boot 分区用的 boot.img（线刷/替换用） |
| `build/rk3588-hlink-h88k.dtb` | 285,685 B | H88K 板级 dtb（Android 化，带 `__symbols__`） |
| `out/SHA256SUMS.txt` | — | 校验和 |

`out/h88k-a14-sd-8g.img` 的分区布局与友善 `parameter.txt` 完全一致：

```
security 4M | uboot_a 4M | uboot_b 4M | misc 4M | dtbo_a/b 4M | vbmeta_a/b 2M
boot_a 64M | boot_b 64M | backup 128M | cache 268M | metadata 64M | frp 512K
baseparameter 4M | super 3.125G | userdata 4.17G
```

idbloader 写在 LBA 64（Rockchip 固定的 32KB 偏移），GPTh 主/备头 CRC 均已自校验通过。

## 二、为什么走 SD 卡，不线刷 eMMC

H88K 的 eMMC 前 32MB 是 Rockchip loader 区、p1 是 U-Boot 的 boot 分区，
**这套 U-Boot 现在负责引导 NVMe 上的 fnOS**。往 eMMC 线刷 Android 会连 loader 一起铲掉，
fnOS 就再也起不来了。

走 SD 卡则完全不碰 eMMC：卡上有自己的 idbloader + uboot_a，
BootROM 扫到卡就从卡启动，拔了卡机器还是原来的 fnOS。

## 三、写卡

Windows 上任选其一，都是**整盘写入**，不要去解压或分区：

- **balenaEtcher**（推荐，写完会自动校验）
- Rufus（选 "DD 镜像模式"，不要 ISO 模式）
- Win32DiskImager

⚠️ 写卡会**清空整张 SD 卡**。8 GiB 镜像写进 ≥8GB 的卡即可（16GB 最省事）。
写完后 Windows 会提示"需要格式化"——**点取消**，那是 Android 的 ext4 分区，Windows 读不懂。

写完自行核对：

```powershell
# 只校验镜像文件本身（Windows 没有 sha256sum 就用这个）
Get-FileHash out\h88k-a14-sd-8g.img -Algorithm SHA256
```

## 四、上电前必须确认的一件事

RK3588 的 BootROM 启动顺序由板上 BOOT 相关引脚/OTP 决定，常见默认是
**SPI NOR → eMMC → SD**。如果这块板子把 eMMC 排在 SD 前面，插了卡也会先从 eMMC 起。

三种处理办法，按顺序试：

1. **直接插卡上电**，看串口有没有 `Boot from SD` 之类的字样（很多板子 SD 优先）。
2. 板上有 **MASKROM / RECOVERY 按键**的，按住上电进 loader 模式，再用
   `rkdeveloptool` 从 USB 走（这条不依赖启动顺序）。
3. 都没有的话，只能临时把 eMMC 的 loader 区擦掉——**这会丢 fnOS 的引导**，
   不建议现在做，先确认前两条。

## 五、串口

- 位置：**GPIO0_B5 (TX) / GPIO0_B6 (RX)**，即 40pin 排针的 pin 13 / 14（`feb50000.serial` = uart2m0）
- 参数：**1,500,000 8N1**，无流控
- 接法：USB-TTL 的 GND 接板子 GND，RX 接板子 TX，TX 接板子 RX
  （**不要接 VCC**，板子自己供电）

```
picocom -b 1500000 /dev/ttyUSB0
# 或
minicom -D /dev/ttyUSB0 -b 1500000
```

## 六、预期现象（按时间顺序）

| 阶段 | 串口 | 屏幕 |
|---|---|---|
| 0-2s | `DDR ...` / `BL31` | 黑 |
| 2-5s | `U-Boot 2017.09 ...`，`Model: HINLINK H88K` | **出现 H88K logo** |
| 5-10s | `Starting kernel ...`，`[ 0.000000] Booting Linux on physical CPU 0x0` | logo 持续 |
| 10-25s | 内核 probe：`dwmmc` `rk808` `hdmi` … | 可能黑一下再亮 |
| 25-60s | `init: ...`，zygote | Android 开机动画 |
| 60-120s | Launcher | 桌面 |

**看到 `Model: HINLINK H88K` 就说明 dtb 生效了**——U-Boot 是从 boot 分区的 resource 段里
读 dtb 打印这一行的。

## 七、出问题怎么判断

| 现象 | 大概率原因 | 下一步 |
|---|---|---|
| 完全没串口输出 | 没从 SD 启动 | 见第四节 |
| 停在 `DDR` 之后 | idbloader 没被读到 | 重写卡；确认卡 ≤32GB、FAT32/exFAT 无关但要是 SDHC/SDXC |
| `U-Boot` 起但 `Model:` 还是 nanopi6 | dtb 没换成功 | 重新 `pack_boot.py`，看 12 槽是否全替换 |
| `Starting kernel` 后立刻死 | dtb 与内核不匹配 / cma 冲突 | 抓完整日志，比对 `build/dtc-h88k.log` |
| 卡在开机动画 | 分区或 super 有问题 | 确认 super 已展开（非 sparse），见 `make_sd_image.py` 输出 |
| `DM_DEV_STATUS failed for system_b` | AVB tries 被扣光，切到空的 `_b` 槽 | 重写卡（本脚本故意不写 misc，让 AVB 重建 `_a, tries=7`） |
| 卡在 logo，`No primary plane find for video_port0` | vop 的 port 缺 plane 绑定 | 本仓 dts 已带 `rockchip,plane-mask`/`primary-plane`，若仍报查这里 |
| HDMI 无输出但有串口 | VOP/PHY 或 EDID | 换口试；`force-output` 已开 |
| 网口不亮 | gmac0 PHY 复位脚/RGMII delay | 查 `&gmac0` 的 `tx_delay` |
| 点"重启"后彻底没反应、PC 出现 `VID_2207&PID_350A` | TF 卡供电被 PMIC 关掉，落 MaskROM | 见下面第 3 条 |

## 八、已知没验证的点

1. **hwrev 探测**：友善 U-Boot 按板上电阻/ADC 挑 `rev01…rev0c` 之一。
   H88K 不是友善板，探测值不可预测，所以 12 个槽**全部**塞了 H88K dtb——
   不管它挑哪个，拿到的都是 H88K 的树。
2. **U-Boot 本身**：用的是友善 rk3588 的 `uboot.img`，里面可能带 T6 的板级初始化
   （DDR 训练参数是 SoC 级的，通常通用；但个别 GPIO/regulator 初值可能不匹配）。
   如果卡在 U-Boot 阶段，第一步是换厂商 A12 的 uboot。
3. **HDMI**：fnOS（mainline 6.18）下两个 HDMI 都是 `deferred probe pending`，
   说明这块板的 HDMI 在非 vendor 内核上本来就有问题。vendor 6.1 + 厂商 dtb 的参数
   应该能出图，但没实测过。
4. **AVB**：底包的 `vbmeta.img` 是空壳（`VERIFICATION_DISABLED` +
   `HASHTREE_DISABLED`，无描述符），所以换 boot.img 不会被校验拦住。
5. **`misc` 故意留空**：不写友善那份 `misc.img`。TM-android14 在 rk3568 上踩过——
   misc 里的 AVB tries 每失败一次扣 1，扣光后 u-boot 按规则切 `_b` 槽，
   而 `_b` 是空的，直接死在 `DM_DEV_STATUS failed for system_b`。
   留全 0 让 u-boot 重建成 `_a, tries=7`。
6. **「重启」可能进 MaskROM**：TM-android14 在 rk3568 上遇到过
   ——`reboot` 时 `dw_mmc.shutdown → mmc_power_off()` 把 TF 卡供电关掉，
   SoC 复位但 PMIC 不复位，BootROM 找不到任何启动介质就落 MaskROM
   （串口 0 输出，PC 出现 `VID_2207&PID_350A`）。
   rk3588 上是否同样，取决于友善 U-Boot 有没有把 sdcard 的 vmmc 标成 always-on。
   **真遇到了就是拔电重上（冷启动），不要以为板子坏了。**

## 九、复现整条链

```bash
# 1) 编 dtb（GitHub Actions，约 50 秒）
#    Actions → dtb-build → Run workflow，产物 h88k-dtb artifact

# 2) 打 boot.img（12 槽 dtb + logo + SHA1 重算 + 容量断言）
python tools/pack_boot.py \
    --stock extracted/android14/boot.img \
    --dtb build/rk3588-hlink-h88k.dtb \
    --logo logos/h88k-lockup-512x128.bmp \
    --kernel-logo logos/h88k-lockup-512x128.bmp \
    -o build/boot-rk3588-h88k-a14.img

# 3) 拼 SD 整盘（GPT + idbloader + 各分区 + sparse 展开 + 回读校验）
python tools/make_sd_image.py --size-gb 8 -o out/h88k-a14-sd-8g.img
```

## 十、dts 依赖闭包是怎么回事

编一个 dtb 本来要整棵内核树（1.5GB+）。友善的 SDK 在 gitea
（`112.124.9.243:3000`），跨境到 GitHub runner 只有 ~200KB/s，
`git clone --filter=blob:none` 跑了 31 分钟连 clone 都没完成。

所以改成本地抓依赖闭包：从板级 dts 出发递归 `#include`，只抓真正用得到的
**27 个文件、455KB**，随仓库带走，CI 侧 `cpp + dtc` 直接编，20 秒出结果。

```bash
python tools/fetch_dts_tree.py --verify    # 校验闭包完整性
```

闭包里一个文件都不能少、也不能被截断（慢链路容易断流），
`--verify` 会把所有 `#include` 逐个解析回本地路径来确认。
