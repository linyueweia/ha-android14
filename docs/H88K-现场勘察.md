# H88K 调试串口 & dts 冲突勘察（2026-11-07）

## 1. 官方口径

iStoreOS 官方 H88K 产品页（site.istoreos.com/firmware/h88k/）原文：

> 其他接口：TF卡槽 / 红外接收灯 / WIFI天线 / **TYPE-C供电接口支持TTL串口调试**
> 供电：DC 12V×1 55201接口、TYPE-C（支持PD和QC协议）
> 启动方式：支持TF卡启动，支持EMMC启动
> 固件支持：ARMBIAN、UBUNTU、ANDROID、OPENWRT

⇒ 官方明确串口调试与 Type-C 供电口相关，但**未给出针脚定义与线序**。

## 2. dts 事实（armbian rk-6.1-rkr5.1 版 rk3588-hinlink-h88k.dts）

```
964  &uart2 { pinctrl-0 = <&uart2m0_xfer>; status = "okay"; };
 41      chosen { stdout-path = "serial2:1500000n8"; };
```

- RK3588 UART2_M0 固定映射：**TX = GPIO1_A0（func 8）/ RX = GPIO1_A1（func 8）**
- 全 dts 仅 3 处 pinctrl 引用：`hdmim1_rx` / `i2c0m2_xfer` / `uart2m0_xfer`
- **无 `pmu_io_domains` 节点**（IO 电压域未显式配置 → 移植 Android 时需补，否则部分 IO 电压可能不对）

## 3. ❌ 已推翻：不存在 GPIO1_A0 冲突（原判断错误，实测更正）

我最初按「RK3588 UART2_M0 = GPIO1_A0/A1」推断 `usbc0_int` 与 `uart2m0_xfer` 抢同一引脚。
**在实机（fnOS, kernel 6.18.18）上读 pinmux 后证明这是错的**：

```
pin 13 (gpio0-13): feb50000.serial (GPIO UNCLAIMED) function uart2 group uart2m0-xfer
pin 14 (gpio0-14): feb50000.serial (GPIO UNCLAIMED) function uart2 group uart2m0-xfer
```

⇒ **UART2_M0 实际是 GPIO0_B5(TX, pin13) / GPIO0_B6(RX, pin14)**，与 Type-C 的
`usbc0_int`(GPIO1_A0) 完全不重叠。husb311 中断正常，串口也正常，两者共存。

教训：UART2_M0 的 bank/pin 不能凭记忆（RK3568/RK3588 不同、M0/M1 不同），必须
`cat /sys/kernel/debug/pinctrl/*/pinmux-pins` 实证。

## 4. 定位物理位置的三种办法（按可行性排序）

1. **拆壳拍照**：主板找丝印 `DEBUG` / `UART` / `CON` / `TX RX GND` / `J??`；H88K 有 mini/pro/max 三版，接口面可能不同
2. **万用表定位**（断电蜂鸣档找 GND，上电直流档看空闲高电平 1.8V/3.3V，上电瞬间有跳变者为 TX）
3. **软件验证**（机器仍跑 fnOS 时）：
   ```sh
   cat /proc/cmdline | tr ' ' '\n' | grep console
   cat /sys/kernel/debug/pinctrl/*/pinmux-pins | grep -iE "uart2|pin (0|1) \(gpio1"
   ```
   若显示 `pin 0 (gpio1-0): husb311` 而不是 `uart2m0-xfer` → 串口被 PD 芯片抢走，接哪都没日志

## 5. 接线参数

- 波特率 **1500000**（1.5M，不是 115200），8N1，无流控
- TX/RX 交叉：板 TX → 线 RX，板 RX → 线 TX，GND 共地，**不要接 VCC**
- 电平：RK3588 UART2_M0 属 1.8V 域（板级未配 pmu_io_domains）；若用 3.3V 的 CH340，高电平可能识别不到，优先用支持 1.8V 的模块或带电平转换的调试线

# 实机勘察结果（2026-11-07 21:10，fnOS @ 192.168.11.171，SSH root）

## 身份

| 项 | 实测 |
|---|---|
| `/proc/device-tree/model` | `Hlink H88K`（注意是 **hlink**，不是 hinlink） |
| `compatible` | `hlink,h88k` `rockchip,rk3588` |
| 内核 | `6.18.18.c1145-trim`（fnOS 自编，mainline 系，非 vendor 6.1） |
| dtb | `/boot/dtb/rockchip/rk3588-hlink-h88k.dtb`（206,620 B，2026-10-28） |
| 内存 | 7.7 GiB 可用 ⇒ **8 GB** |
| cmdline | `console=ttyS2,1500000 ... cma=256M` |

## 存储（关键：决定 Android 装哪）

```
mmcblk1  58.3G  eMMC(64GB)  ← GPT, 前 65536 扇区(32MB) 为 raw loader 区
  p1  380M  Linux extended boot  ← ubootpart，U-Boot 的 /boot 分区
  p2  3.2G  Linux filesystem
nvme0n1 931.5G  ← fnOS 系统盘（/ 在 p1 64G，p2 867G 为 RAID1+LVM /vol1）
ata_link/link1 存在，sata_spd = unknown（SATA 控制器有，当前无盘/未协商）
```

⚠️ **eMMC 承载 U-Boot**（cmdline `ubootpart=PARTUUID=22b17fb3...` = mmcblk1p1）。
⇒ 把 Android 刷进 eMMC 会覆盖 U-Boot，NVMe 上的 fnOS 将无法启动。
⇒ 现阶段**只做 SD 卡启动**，eMMC 一个字节都不动。

## 显示（⚠️ 风险项）

```
[16.108] platform hdmi0-sound: deferred probe pending: asoc-simple-card: parse error
[16.108] platform fdea0000.hdmi: deferred probe pending: (reason unknown)
[16.108] platform hdmi1-sound: deferred probe pending: asoc-simple-card: parse error
/sys/class/drm/ 只有 card0 / renderD128 / version —— 没有 card0-HDMI-A-1 连接器
```

⇒ fnOS 的 mainline 6.18 下 **两个 HDMI 都没注册输出连接器**。
Android 侧走 vendor 6.1 + 友善 HDMI 驱动，环境不同，但这是必须先验证的红线：
没有可用显示 ⇒ SurfaceFlinger 起不来 ⇒ 卡开机。

## 串口参数（最终）

- 设备：`/dev/ttyS2`（`feb50000.serial`）
- 引脚：**TX = GPIO0_B5 / RX = GPIO0_B6**（func 8, uart2m0-xfer）
- 波特率 1500000 8N1，无流控
- 电平：GPIO0 属 PMU IO 域，多为 **1.8V**。若用 3.3V 的 CH340，板 TX→线 RX 可能因
  阈值不够而收不到（表现为"接了没反应"）。先量 TX 空闲电压再决定要不要换 1.8V 线。
